Building Nomisma

Inception: a place for the workshops and collaboration

1 October 20265 min read

I've created Nomisma Labs on GitHub as a home for reusable trading components and the tools used to develop them. I'm taking the component-based approach from my earlier trading-platform project a step further by organizing development into workshops. Their products can be combined to build different kinds of trading systems.

Each workshop develops a component with a specific responsibility, such as configuration, event processing, logging or communication. The workshop owns that component's implementation, API, dependencies, tests, documentation and release cycle. The workshops collaborate, and their products become building blocks for complete applications.

A high-frequency trading (HFT) application may need dedicated latency benchmarks and tight control over its market-data and execution paths. A mid-frequency trading system may focus on flexible workflows and operational integration. Market connectivity, execution models, risk controls and deployment requirements also affect which components belong together.

A Git repository serves as a container for a component or a workshop. Git submodules will record dependency revisions, and the build system will integrate the C++ libraries. The workshops will share a CMake-based toolchain for consistent targets, tests and packaging.

I also want a clear boundary between a workshop and its product. The workshop contains the full development environment, including source code, experiments, CI/CD, comprehensive tests, documentation and tooling. The distributed product gives its users the code, user documentation, tests and build support they need. Public products will use an open-source licence. Distribution terms can be chosen separately for each component.

In many cases, "Git repo", "component", "product" and "workshop" refer to the same thing, so the terms can be used interchangeably. Each term still has a distinct meaning.

  • A component is a software entity whose API defines its functional boundaries.
  • A product is a released component ready for distribution and use by its clients.
  • A workshop is a development environment for creating and releasing a component or a system.
  • A Git repo is a container for the source code of a component, a workshop or both.

Here's how they fit together.

  • For component development, each workshop contains a single component and produces one or more releases. Each release is a distinct version of the product.
  • A product can be distributed as versioned component source code, optionally with a build system and documentation. Packaged forms include executable binaries, Python modules and Docker containers.
  • For now, a workshop and its Git repo are one and the same because the toolchain is tightly coupled to the component's source code. I plan to separate the toolchain from the component later.
  • Git is used to tag each version of a component, and Git submodules are used to record the components it depends on and their exact revisions.

Explanatory notes (optional)

Why not a monorepo?

I find a monorepo works best when one team develops one product on a single release cycle. In that setting, one repo keeps operational overhead low. In trading system development, research, trading, platform development and infrastructure work are only loosely coupled. They require different skills, and a change that's urgent for one group may have little bearing on another group's release schedule.

Imagine optimization work taking place in parallel with the introduction of a new market to the trading platform. Even with careful use of Git branches, the two changes cancel each other out and lead to unmanageable conflicts. Trading strategy logic is also typically kept separate from platform development because traders prefer not to share their secrets.

Why a "workshop" model?

This is an attempt to marry different styles of software development in a single project. Consider the differences between proprietary software development within one organization, off-the-shelf software and open-source projects. They assume different levels of collaboration, openness and responsibility.

For instance, an open-source repo usually contains everything related to the project, including the source code, build system, docs, tests and tooling. When you buy a video game, you get only a downloadable package containing a prebuilt binary and the resources required to run the game on your platform. The package doesn't include a game location editor.

The focus of Nomisma Labs is trading platform development, but what kind of trading platform? Crypto, capital markets or FX? HFT or MFT? These are only the most obvious differences. Some parts of a trading platform are meant to be public, some are strictly private and some are hybrid.

What about development for multiple platforms, C++ versions or languages?

This isn't supported for economic reasons. It's possible to cover all these differences with multiple toolchains, support for multiple build systems and a carefully designed C++ abstraction layer that lets you write code for a range of C++ compilers and standards. Boost is one of many examples. Yes, it's possible, but it's costly. The workshop model still leaves people free to create their own workshops with their own compatibility requirements.

Why a single toolchain?

This is a specific case of the previous question. The difference here is that the current code structure doesn't allow the component source to be separated from the toolchain. The reason is still the cost. I plan to change this by drawing a clear boundary between the toolchain and the component.
