Building Nomisma

Inception: a place for the workshops

1 October 20262 min read

I've created Nomisma Labs on GitHub as a home for reusable trading components and the tools used to develop them. The idea is a group of workshops whose products can be combined into different trading systems. It carries forward the component-based approach from my earlier trading-platform project.

Each workshop concentrates on a particular responsibility: configuration, event processing, logging or another part of the system. It owns the component's API, dependencies, tests and release cycle. The workshops collaborate through those interfaces, and their products become building blocks for complete applications.

The combination depends on the system. An HFT application may need dedicated latency benchmarks and tight control over the market-data and order paths. A mid-frequence trading system may focus on flexible workflows and operational integration. Market connectivity, execution models, risk controls and deployment requirements all affect which components belong together.

The plan is one component per repository, with a separate trading system repository selecting compatible versions. Git submodules will record dependency revisions, and CMake's FetchContent will integrate the C++ libraries into the build. Shared CMake infrastructure will provide consistent targets, tests and packaging. Components should work both from source and as installed packages, so integration checks need to exercise both forms.

This structure lets workshops develop independently while making compatibility an explicit responsibility of the system repository. Several systems can share configuration or logging without sharing every execution component, policy or performance requirement.

I also want a clear boundary between a workshop and its product. The private workshop contains the full development environment: source, experiments, CI/CD, comprehensive tests, internal documentation and tooling. A distributed product contains the code, documentation, tests and build support its users need. Public products will use an open-source licence; distribution terms can be chosen per component or client.

In terms of included material, product ≤ workshop. A release may include some or all of the workshop, and a complete handover can include the development setup too. Internal tooling such as cmake_template can remain entirely within the workshops as non-distributable component.

I chose GitHub for visibility and collaboration, although I preferred GitLab's CI/CD workflow. Public products give other developers something they can inspect, build and evaluate. That makes open source a practical way to introduce the work and find people who can use or contribute to it.

The first step is the common CMake template. It will give the workshops a consistent starting point for building, testing and connecting their components.
