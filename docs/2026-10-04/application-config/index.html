Building Nomisma

Application config

4 October 20262 min read

I'm starting work on the application config framework toml_config. Configuration is the next part of the core layer after Assembly/Relay. The choice of TOML as a configuration format is almost arbitrary. I wanted to try anything except JSON, and of the modern trinity of config formats (JSON, YAML and TOML), TOML looks the least complex and seems built for the purpose. I hadn't worked with TOML before, so this decision is mostly an experiment.

I'm talking about app config, but what I actually want is a configuration management system. In many of my previous projects, I used a type of stackable config system that lets you structure the final app config using config layers that typically correspond to the applicable environments, e.g. dev -> integration -> prod. I extended this approach to support more ways of structuring the config and added tooling to make it more convenient, but the main idea is still the same. The app config is represented by one or more config parts that define parameters for the whole app or a single component in one or more environments. You can check the details in the repo documentation (see TOML, JSON or YAML docs).

Indeed, a config is important, but from a user's standpoint, it could be the last part of the app they would look at. A config can also become the biggest dependency of an app (over time, config parameters tend to creep into every aspect of a complex system). For this reason, I put extra effort into making it an optional and replaceable part of an app.

Update: I later implemented config frameworks for the two other formats (json_config and yaml_config). They share many similarities and will probably be merged into a single app config framework with format selection.
